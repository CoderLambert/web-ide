## Fixture and method

- Deterministic in-memory SQL generator; no large fixture is committed.
- Sizes: 10KB, 100KB, and 1MB (actual generated size is reported below).
- 100KB shapes: realistic multi-statement SQL and large-statement / worst-case SQL.
- Incremental benchmark: warmup 10, measurement 100; one UTF-16 identifier character replaced at the file start, middle, and end for 100KB.
- 1MB: full open baseline plus one middle incremental edit; Worker must remain alive.
- Continuous 1MB EditCodec benchmark: realistic multi-statement SQL at the middle and end, warmup 10, measurement 100.
- Full parse baseline uses 3 samples below 1MB and 1 sample at 1MB.
- RTT is measured around TreeSitterClient.request; parse time is Worker ParseResult.parseTimeMs.
- changedRanges coverage is reported from the ranges returned by the Worker. The low-structure identifier replacements in this run returned zero ranges, so their reported coverage is 0%.
- EditCodec auxiliary metrics are sparse per transaction; no document-size auxiliary TypedArray is allocated.

## Root-cause judgment

100KB incremental RTT P95 (2.70 ms) is materially above parse P95 (0.70 ms). The dominant cost is outside parser.parse; the isolated EditCodec P95 is 0.20 ms, so the remaining gap is Worker/client messaging and changed-range conversion. The baseline before commit `10d8095` showed EditCodec P95 up to 222.40ms, identifying repeated UTF-16 to UTF-8 scans and per-code-point TextEncoder calls as the dominant source of the original latency. The follow-up sparse boundary scan keeps auxiliary metrics at O(changes) and allocates no document-size Uint32Array. No Protocol profiling field or architectural rewrite was added.

The prior approximately 270–291ms observation was therefore treated as a diagnostic signal, not an automatic reason to introduce Rope, Piece Table, persistent indexes, Worker Pool, Parser Pool, grammar changes, or dependency upgrades.
